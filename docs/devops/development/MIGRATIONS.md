# Database Migrations Guide

> ANT uses Alembic for versioned SQLAlchemy schema migrations. This guide covers day-to-day use, the `ANT_SKIP_ALEMBIC` escape hatch, and the integration with `DatabaseManager.initialize()`.

---

## 1. Quick reference

| Task | Command |
|---|---|
| Apply all pending migrations | `make alembic-upgrade` (or `cd backend && alembic upgrade head`) |
| Roll back one migration | `cd backend && alembic downgrade -1` |
| Roll back everything | `cd backend && alembic downgrade base` |
| Show current version | `cd backend && alembic current` |
| Show migration history | `cd backend && alembic history` |
| Generate a new migration | `make alembic-revision MSG="add foo table"` |
| Stamp DB at head (no run) | `cd backend && alembic stamp head` |

---

## 2. How the backend uses Alembic

`backend/core/database.py:DatabaseManager.initialize()` does this at startup:

1. Run `alembic upgrade head` in a **worker thread** (to avoid the "asyncio.run from running loop" conflict when the FastAPI lifespan starts).
2. Then run `Base.metadata.create_all()` as a safety net for any tables the migration missed.
3. The whole thing is **idempotent**: on a second `init_database()` call, alembic sees the DB is at HEAD and skips.

```python
# In DatabaseManager.initialize()
def _run_migrations_blocking():
    from alembic.config import Config
    from alembic import command
    cfg = Config("backend/alembic.ini")
    cfg.set_main_option("script_location", "backend/migrations")
    command.upgrade(cfg, "head")

if not os.environ.get("ANT_SKIP_ALEMBIC"):
    migration_thread = threading.Thread(target=_run_migrations_blocking, daemon=True)
    migration_thread.start()
    migration_thread.join(timeout=60)
```

The `backend/migrations/env.py` file imports `Base` from `core.database` so autogenerate sees the real schema. It also resolves the DB URL from the same env vars the app uses (`DATABASE_URL` / `USE_SQLITE` / `FORCE_SQLITE` / `CLOUD_MODE`).

## 3. Adding a new model

### Step 1 — Edit the model

Add the model class to `backend/core/database.py` (or whichever submodule owns it). All models inherit from `Base = declarative_base()`.

```python
class JobListing(Base):
    __tablename__ = "job_listings"
    id = Column(Integer, primary_key=True)
    title = Column(String, nullable=False)
    company = Column(String, nullable=False)
    url = Column(String)
    created_at = Column(DateTime, default=datetime.utcnow)
```

### Step 2 — Generate a migration

```bash
make alembic-revision MSG="add JobListing table"
# or:  cd backend && alembic revision --autogenerate -m "add JobListing table"
```

Alembic inspects `Base.metadata` and generates a file in `backend/migrations/versions/` with the diff. **Always review the autogenerated file** — alembic sometimes misses things like `server_default`, index renames, or column-type changes.

### Step 3 — Edit the migration (if needed)

Common things to add manually:

```python
def upgrade():
    op.create_table(
        "job_listings",
        sa.Column("id", sa.Integer, primary_key=True),
        sa.Column("title", sa.String, nullable=False),
        sa.Column("company", sa.String, nullable=False),
        sa.Column("url", sa.String),
        sa.Column("created_at", sa.DateTime, server_default=sa.func.now()),
    )
    op.create_index("ix_job_listings_company", "job_listings", ["company"])

def downgrade():
    op.drop_index("ix_job_listings_company", table_name="job_listings")
    op.drop_table("job_listings")
```

### Step 4 — Apply the migration locally

```bash
make alembic-upgrade
# or:  cd backend && alembic upgrade head
```

### Step 5 — Test the roundtrip

```bash
cd backend && alembic downgrade base && alembic upgrade head
```

This drops everything and re-applies all migrations from scratch. It should succeed with no errors.

### Step 6 — Commit + push

The migration file is committed with the model change. On the next deploy, `DatabaseManager.initialize()` will run it automatically.

## 4. The `ANT_SKIP_ALEMBIC` escape hatch

Set `ANT_SKIP_ALEMBIC=1` to disable the migration step entirely. Use cases:

- **Tests** — they build a fresh in-memory DB via `Base.metadata.create_all()` and don't need migrations.
- **Read-only replicas** — the app starts but never writes schema changes.
- **CI sandbox** — when running against a throwaway database.

The flag is set in `backend/tests/conftest.py:14` so all unit tests skip the migration step.

## 5. Adding an Alembic data migration (not schema)

If you need to backfill data, use a separate revision:

```python
# alembic revision -m "backfill user emails"
def upgrade():
    # Read the data, transform, write back
    conn = op.get_bind()
    conn.execute(sa.text("UPDATE users SET email = LOWER(email) WHERE email IS NOT NULL"))
```

**Rule of thumb:** if your migration is destructive (drops a column, changes a type), always:
1. Test it on a copy of production data first.
2. Have a tested `downgrade()`.
3. Coordinate the deploy with a brief maintenance window if the migration takes > 1 minute on a large table.

## 6. Troubleshooting

### "Can't locate revision identified by 'XXXX'"

The migration file is missing from `backend/migrations/versions/`, or the `alembic_version` row in the DB points to a revision that doesn't exist in the file tree.

Fix: copy the file in from git, OR `alembic stamp head` to skip it (only if you know the schema is already at the right state).

### "alembic_version is None" after `alembic upgrade head`

The migration ran but didn't stamp `alembic_version`. This is a bug in the migration file — make sure it ends with `upgrade()` and not an early `return`.

### "FAILED: alembic init stamping"

The audit's "Pre-existing test failures" doc flagged this. `init_db()` (in some test fixtures) only runs `Base.metadata.create_all()`, not `alembic upgrade head`. To fix: add `from alembic import command; command.upgrade(alembic_cfg, "head")` to the fixture, OR set `ANT_SKIP_ALEMBIC=1` in the test and accept that the test DB is unversioned.

### "Table 'X' already exists"

The DB was created with `create_all()` BEFORE alembic ran. Either:
- Drop the tables manually: `alembic downgrade base && alembic upgrade head`
- OR stamp the DB at head: `alembic stamp head` (this tells alembic "trust me, we're at head" without running any migrations)
